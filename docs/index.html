What you can do

Capabilities depend on configuration, permissions and the deployed image pair. Consult current source and operational guides.

Inspect incident evidence

Incident context brings resource details, logs, previous logs and events together. Lifecycle views connect findings, investigations, actions and verification.

Review proposed repairs

The inbox and agent confirmation surfaces let users review actions. Approval does not override backend permissions or namespace/node policy.

Follow actual outcomes

Lifecycle views separate proposed, executed and verified actions, show verification evidence and handle recurrence. A model-written resolution checklist is not proof of recovery.

Keep cluster targets explicit

Resource reads and supported operations retain their selected cluster target across switches. Local agent context is distinguished from remote fleet resource context.

Readiness and recovery evidence

Use a matched agent/UI release. Installation diagnostics come from the agent and can remain unknown; cluster permissions, actual provider behavior and sustained repair need separate tests. Isolated UI acceptance uses controlled responses and certifies no live cluster.

Crashloop, failed rollout and pending-pod acceptance must preserve diagnostic observations, the exact approved target/change, execution results and fresh recovery measurements. Rejected or unverifiable operations stay unresolved.
